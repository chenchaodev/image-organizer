# 技术栈选型分析(2026-08-18 21:45:00)

> 初始化工程时的选型分析原文。结论摘要见 docs/ADR.md(ADR-01/ADR-02)。

## 需求约束

- 跨平台桌面(Win/Mac/Linux)
- 本地非破坏式图片库:1万~10万张个人图片
- 核心功能:整理归类、重复检测(pHash)、批处理(重命名/转换/压缩)
- 无既有代码/技术偏好,从零选型

## 桌面框架对比

| 维度 | Tauri 2 | Electron | Flutter Desktop | PySide/Qt |
|---|---|---|---|---|
| 安装体积 | ~10MB | ~100MB+ | ~20MB(编译产物) | ~50MB+ |
| 内存占用 | 低 | 高 | 中 | 中 |
| 后端性能(扫描/哈希/缩略图) | Rust:极强 | Node:中 | Dart:中 | Python:弱 |
| 文件系统/原生能力 | 强(Rust 生态) | 中 | 需插件 | 强(Qt) |
| 跨平台 | Win/Mac/Linux | 全 | 全 | 全 |
| 打包分发 | 中(NSIS/AppImage/dmg) | 中 | 中 | 繁琐 |

结论:10万张图片的扫描、感知哈希、缩略图生成、格式转换是 CPU/IO 密集任务,Rust 后端优势明显;Tauri 2 体积/内存优势大。选 Tauri 2。

## 前端方案

- React 19 + Vite 7 + TypeScript:生态最大,TanStack Virtual 虚拟滚动成熟,10万条目网格性能有保障
- 备选:Svelte 5(更轻但生态较小)、Vue 3(生态好,团队偏好未知)
- 结论:React 19。

## 数据库对比

| 维度 | SQLite(WAL) | DuckDB | Postgres(本地) |
|---|---|---|---|
| 部署 | 单文件零配置 | 单文件 | 需服务进程 |
| 10万行查询 | 毫秒级 | 毫秒级 | 毫秒级 |
| FTS 全文搜索 | FTS5 内置 | 无内置 FTS | 好但重 |
| 生态(rusqlite/sqlx) | 成熟 | 较新 | 需服务 |
- 结论:SQLite + WAL。理由:零配置、单文件、FTS5 满足后续搜索需求。

## 图片处理与去重算法

- image crate:Rust 标准解码/编码库(JPEG/PNG/WebP/GIF),缩略图与转换用
- img_hash crate:感知哈希(dHash/pHash/aHash),用于相似检测
- exif crate:元数据读取
- 去重策略:pHash 粗分桶(按哈希前若干位分组)→ 桶内汉明距离细比较,避免全库 O(n²);10万张规模下桶内比较量可控
- 备选:自实现 dHash(可控但重复造轮子);特征点匹配 ORB/SIFT(过重,相似而非重复检测才需要)

## 风险与对策

1. 首扫 10万张耗时 → 增量扫描(mtime+size)+ 多 worker 并发管线,目标 <10 分钟量级
2. 缩略图生成瓶颈 → 后台队列(tokio mpsc)+ 分级缓存(WebP),懒加载
3. Windows 编译环境 → MSVC Build Tools 必需;工具链镜像走华科/中科大
4. 去重精度 → 桶边界补偿策略待 M2 实测评估
