## 1. Rust HEIC/HEIF 解码 —— 推荐 libheif-rs

**结论:选 `libheif-rs 2.7.0`**(2026-02-25 发布,活跃维护,55 万+ 下载,25 dependents)+ `libheif-sys 5.3.0+1.23.0`(内嵌 libheif 1.23.0 源码)。这是 Rust 生态唯一成熟方案。

### Windows:不能纯 cargo 构建,必须 vcpkg
- libheif-sys 在 Windows 用 `vcpkg` crate 找库;官方路径 `cargo vcpkg -v build`(自动下载构建 vcpkg 包)或手动 `vcpkg install libheif`(port 当前 v1.23.1#0,2026-07-03)
- `embedded-libheif` feature 可静态编译内嵌 libheif,但 README 明确其依赖 libde265/libaom 等仍需外部提供,且 CHANGELOG 注明 compile-libheif 系列不支持 Windows → 不能绕开 vcpkg
- vcpkg 步骤:`git clone https://github.com/Microsoft/vcpkg.git && ./bootstrap-vcpkg.bat && ./vcpkg integrate install && vcpkg install libheif`。HEIC 解码依赖 libde265(vcpkg 默认带);`hevc`(x265 编码,GPL)是默认 feature,可 `libheif[core,libde265]` 规避 GPL(PR #36857)
- 镜像:vcpkg 无官方国内镜像;vcpkg 本体与源码包走 GitHub,国内慢需代理;CI 建议 actions/cache 缓存 vcpkg 目录(libheif+libde265 编译约 5-15 分钟)

### macOS/Linux 顺畅
- macOS:`brew install libheif`(有 bottle,Apple Silicon/Intel 均支持)
- Ubuntu:`apt install libheif-dev`(noble=1.17.6,25.10=1.20.2,依赖 libde265-dev)
- 坑:Fedora 默认 libheif 不含 HEIC(专利),需 RPM Fusion libheif-freeworld(image-rs issue #1375 原话)——CI 用 ubuntu-latest 即可

### Tauri 2 集成坑
- 无 libheif 专属问题,但 C++ 依赖通用坑:Tauri 以 MD_DynamicRelease 链接,静态 C++ 库会 LNK2038(tauri issue #9374);vcpkg 默认 x64-windows triplet 产 DLL 无此问题
- 打包需随应用分发 heif.dll/libde265.dll(libheif-sharp 文档有 DLL 清单)

### 替代方案对比
| 方案 | 结论 |
|---|---|
| `heif` crate | 停更多年,绑 libheif 1.x,不选 |
| `image` crate 0.25.10 | 无 HEIC(issue #1375,专利+项目政策),仅用于 JPEG/PNG/WebP/AVIF 与缩略图处理 |
| `@napi-rs/image` | HEIC 仅 macOS(ImageIO)/Windows(WIC),Linux 不支持,且是 Node 包,三平台需求出局 |
| exiftool/ffmpeg 外部进程 | 每张进程开销大、三平台打包体积大,100k 张不可行 |

### 性能量级
- 12MP iPhone HEIC 解码 ~100-300ms(tifig 实测 97-113ms;libheif #645:M2 上 0.166s/6 线程);4K ~0.8s(i7-4770k);60MP 索尼 HIF 多线程 1.5-2.7s(#1787)
- 内存:12MP RGBA 全解码 ≈48MB/张
- 关键优化:HEIF 内嵌缩略图——iPhone 照片自带 320x212/1616x1080 缩略图,libheif-rs `ImageHandle::number_of_thumbnails()/thumbnail()` 可直接解码(毫秒级、内存极小),无内嵌才全尺寸解码

| 库 | 版本 | 维护 | 网格 | React 19 |

## 3. 缩略图最佳实践

- image crate `thumbnail()`:快速整数算法(每源像素只贡献一个目标像素),新尺寸接近原尺寸时有锯齿(docs 原文);2000x2000→150x150 实测 13ms。质量优先用 `resize(FilterType::Triangle)`(70ms);Lanczos3 607ms 太慢
- 必须 release 构建(debug 慢 40 倍,issue #1424)
- 缓存格式选 WebP(q80):image 0.25 支持 WebP 与 AVIF 编码;AVIF 编码(ravif)CPU 极重,100k 张不划算;WebP 编码快、体积小、解码通用
- 并发用 rayon:解码是 CPU 密集阻塞任务,`par_iter` 按核调度;tokio 适合 I/O,CPU 密集需 spawn_blocking+信号量多一层
- libheif 内部默认 4 线程 tile 解码(`heif_context_set_max_decoding_threads` 可调),避免 4 线程×N 并行超订——建议每 context 限 1-2 线程或 rayon 并行度=核数/4;Tauri 侧用 `spawn_blocking` 包住避免阻塞主线程
